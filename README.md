# Do LLMs Know Tool Irrelevance? — Reproduction Code

Reproduction code and dataset for the ACL 2026 paper
**"Do LLMs Know Tool Irrelevance? Demystifying Structural Alignment Bias in Tool
Invocations"** ([`assets/2026.acl-long.1473.pdf`](assets/2026.acl-long.1473.pdf)).

The paper identifies **structural alignment bias**: even when a tool is
*semantically irrelevant* to a query, LLMs tend to invoke it whenever the
query's attributes can be validly assigned to the tool's parameters
(*structural alignment*). The repo lets you:

1. Load the **SABEval** dataset;
2. Reproduce the **behavior analysis** — Tool Invocation Rate (TIR);
3. Reproduce the **mechanistic analysis** — Contrastive Attention Attribution
   (CAA) — and the attention-scaling mitigation.

## 1. Environment

Managed with [uv](https://docs.astral.sh/uv/). Python 3.12, CUDA 12.1 wheels.

```bash
uv sync                # creates/updates .venv from pyproject.toml + uv.lock
cp .env.example .env   # then edit CUDA_VISIBLE_DEVICES
```

Run commands either with `uv run python ...` or after `source .venv/bin/activate`.

## 2. Models

Five tool-use models are evaluated: `qwen3-4b`, `qwen3-8b`, `qwen3-14b`,
`toolace-2.5-8b`, `watt-tool-8b`. Point the registry at your local HuggingFace
snapshots by editing the paths in
[`model_utils/model_config.py`](model_utils/model_config.py). Qwen3 runs with
thinking mode disabled, consistent with the paper.

## 3. The SABEval dataset (`data/SABEval/`)

SABEval decouples structural alignment from semantic relevance using the OOP
*polymorphism* principle: sibling tools share one interface (parameters) but
have mutually exclusive functionalities.

| Folder | Contents |
|---|---|
| `tool_templates/` | 101 tool templates. Each carries a `tool_template` with a `<class>` placeholder, a `base_class`, its `derived_classes`, plus optional additional parameters used to build D₁–D₄. |
| `queries/add{0..4}/` | GPT-4o-generated `queries` per derived tool, keyed by `tool_template_name`/`derived_class`. `add{k}` corresponds to subset Dₖ (k additional attribute–parameter assignments). |
| `sibling_pairs/` | The 10 `sibling_pairs` `(query_derived_class, tool_derived_class)` per template. Each pair instantiates a tool for one derived class and pairs it with a query written for a *different* sibling class — so the tool never actually serves the query, yet every query attribute maps onto a tool parameter. |

Total: 101 templates × 10 sibling pairs × 5 queries = **5,050 instances** per subset Dₖ.

## 4. Reproduction

### 4a. Behavior analysis (section 4 — Table 1, Fig 3, Fig 4, Table 4)

```bash
CUDA_VISIBLE_DEVICES=0 bash behavior_analysis/run_behavior.sh
```

This runs [`behavior_analysis/generate_data.py`](behavior_analysis/generate_data.py),
writing, for every (model, mode, add), the next-token `logits_info` for each of
the 5,050 SABEval instances to `data/<model>/<mode>_add_<k>.json`. TIR is the
fraction of instances where the tool-call token is the argmax next token
(`logits_info.tool_call_token_rank == 0`). It also runs
[`get_refuse_tokens.py`](behavior_analysis/get_refuse_tokens.py) for Table 8.

Then open the notebooks (they auto-locate the repo root; launch Jupyter anywhere):

| Notebook | Paper result |
|---|---|
| `notebooks/table1_random_vs_sabeval.ipynb` | Table 1 (random pairing vs SABEval D₀) |
| `notebooks/fig3_alignment_degree.ipynb`    | Fig 3 (TIR vs alignment degree)         |
| `notebooks/fig4_counterfactual.ipynb`      | Fig 4 / Table 4 (structural counterfactuals) |
| `notebooks/fig8_dataset_stats.ipynb`       | Fig 8 (dataset statistics)              |

### 4b. Mechanistic analysis (section 5 — Fig 5–7, Table 3)

First compute the CAA attribution tensors, then the downstream analyses:

```bash
# 1. Attribution (semantic and structural circuits on D_1 train)
CUDA_VISIBLE_DEVICES=0 bash mech_analysis/run_attribution.sh

# 2. Fig 7 heatmaps (single-coefficient sweep on test)
python -m mech_analysis.scale_search_single

# 3. Fig 6 / Fig 18 (pathway strength)
python -m mech_analysis.evaluate_compare

# 4. Table 3 (grid-search rho on val, then evaluate on test)
python -m mech_analysis.scale_search
python -m mech_analysis.evaluate
```

| Notebook | Paper result |
|---|---|
| `notebooks/fig5_pathways.ipynb`         | Fig 5 (semantic / structural pathways)               |
| `notebooks/fig6_pathway_strength.ipynb` | Fig 6 (pathway strength, invocation vs no-invocation) |
| `notebooks/fig7_scaling_heatmaps.ipynb` | Fig 7 (TIR vs scaling coefficient)                    |
| `notebooks/table3_main_results.ipynb`   | Table 3 (Base / Prompt / CAA on D₀–D₄)                |

## 5. Repository layout

```
data/SABEval/       the dataset (tracked)
data/<model>/       per-model logits (regenerated by run_behavior.sh; git-ignored)
results/            attribution tensors and patch results (regenerated; git-ignored)
model_utils/        model wrappers (TransformerLens) + model registry
utils/data_util.py  SABEval loaders + logits-data builder (create_data / create_exp)
behavior_analysis/  behavior data + refusal tokens + run_behavior.sh
mech_analysis/      CAA attribution, edge patching, scaling, evaluation + run_attribution.sh
notebooks/          one notebook per figure/table
```
